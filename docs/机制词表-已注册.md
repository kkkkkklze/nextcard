## 一、核心设计：合成方式属于槽位，不属于卡面

这是本次注册唯一重要的架构决定。规格 §5.4 的"修饰槽位"落成后，**每个槽位自己声明
多张卡改写它时怎么合并**，卡面只有一个数值，写不出第二种解释：

| 合成方式 | 含义 | 用在 |
| --- | --- | --- |
| `SET` | 覆盖；两处给不同的值 = **加载期报错**（矛盾必须显式解决） | 语义唯一的开关（能否取消蓄力、窗口基础值） |
| `ADD` | 加算 | 窗口延长项、蓄力速度、各数值通道 |
| `MULTIPLY` | 乘算 | 乘区 |
| `DIVIDE` | 除法项 | 判定难度（÷3、÷2） |
| `MAX` | 取最宽松 | 上限类（层数上限、减伤上限、蓄力条上限） |
| `UNCAPPED` | 解除上限（布尔式，无值） | "不再有上限"类卡 |

因此卡表里那些**互相矛盾的写法**在结构上被消解了：

| 卡表原话 | 语汇里的答案 |
| --- | --- |
| 节奏记忆"不可单独叠加，如有【时机感知】则乘法叠加" vs 池说明"延长项走加法" | **已裁定（klze，2026-09-25）**：延长项 `window.length` 保持 `ADD` 不变，**乘算改由独立槽位 `window.scale` 承载**，该卡写 `window.scale`。两条链正交，互不覆盖；`ParryChargeVocabularyTest` 第 48–50 行就是这种三条来源并存的合成 |
| 壁障上限"3 层"→"最多 10 层"→"上限解除" | 声明给基准（3），改写走 `MAX`（10），解除走 `uncapped`（事实而非大数字） |
| 蓄力条"每张招式卡给出上限"+"开山 +2 秒" | `charge.bar_max` 声明 `MAX`（取最高）、`charge.bar_bonus` 声明 `ADD`（加算），两条链天然并存 |
| 战意每层蓄力速度 "+3%"（池说明） vs "+20%"（器灵苏醒） | **已裁定（klze，2026-09-25）**：先按 `charge.rate` 的 `ADD` 叠加，不拆槽位。折叠口径：`每层 +3%` 按层数线性放大（3 层＝+9%），与另一条固定 `+20%` 相加＝+29%；若它们其实是"替代"关系（器灵苏醒覆盖池说明），要改成不同槽位，这条留给内容侧按卡面逐张定 |
| "减伤不再有上限"与"减伤翻倍"同时在场 | 分别落在 `block.reduction_cap`（`MAX` + 解除）与 `block.reduction_scale`（`MULTIPLY`），互不覆盖 |

## 二、槽位词表

### 事件（`trigger.on`，只能被监听）

`attack` · `hit` · `kill` · `tick` · `damage_taken` · `damage_dealt` · `block_success` ·
`parry_success` · `parry_fail` · `charge_release` · `charge_interrupt` · `control_immune` ·
`shield_down` · `stand_still` · `skill_cast`

### 参数（`mechanic_modifier.target`）

| 槽位 | 合成 | 用途（卡表来源） |
| --- | --- | --- |
| `window.base` / `window.length` / `window.scale` / `window.difficulty` | `SET` / `ADD` / `MULTIPLY` / `DIVIDE` | 精准格挡判定窗口（时机感知、节奏记忆、绝境读秒、反射神经、忘我之境） |
| `block.angle` | `MAX` | 格挡角度档，值写字符串：`front` < `front_side` < `all`（举盾习惯 / 全向盾墙 / 盾之誓约；两张卡各写一档时取最宽松） |
| `block.reduction` / `block.reduction_scale` / `block.reduction_cap` | `ADD` / `MULTIPLY` / `MAX` | 格挡减伤与其上限（稳手 20%、不动如山翻倍、盾之誓约解除） |
| `parry.reward_cap` | `MAX` | 弹反誓约"奖励不再有上限" |
| `charge.bar_max` / `charge.bar_bonus` | `MAX` / `ADD` | 蓄力条上限（招式卡 + 开山 +2 秒） |
| `charge.rate` | `ADD` | 蓄力速度（沉肩站定 +30%、战意每层） |
| `charge.resolve` / `charge.resolve_cap` | `ADD` / `MAX` | 本次蓄力的最终倍率及其上限（借力、稳桩、器灵苏醒） |
| `charge.damage_taken` / `charge.control_duration` | `ADD` | 蓄力期间受伤 +25%、受控时长 −30% |
| `charge.cancelable` / `charge.interruptible` | `SET` | 势不可回（不可取消）/ 蓄势不泄（不再被打断） |
| `stack.<叠层 id>.cap` / `.duration` | `MAX` | 任何叠层资源的上限与时长 |
| `stack.<叠层 id>.gain` | `ADD` | 产出修正 |
| `channel.<通道>` | `ADD` | 附带数值（见下） |

### 数值通道（附带数值的落点）

`armor` `max_health` `max_health_scale` `move_speed` `attack_speed` `crit_chance` `crit_damage`
`all_damage` `physical_damage` `melee_damage` `base_damage` `direction_bonus` `backstab_bonus`
`armor_pierce` `lifesteal` `resistance` `damage_reduction`

- **点值通道**（卡面写 "+10 护甲值"）：`armor` `max_health` `base_damage`
- **能直接落成原版 AttributeModifier 的**：`armor` `max_health` `max_health_scale` `base_damage`
  `move_speed` `attack_speed`（点值走 ADDITION、比值走 MULTIPLY_TOTAL，分法由 `FLAT_CHANNELS` 声明）；
  其余进自定义伤害管线。注意 `max_health` 与 `max_health_scale` 是<em>同一条属性上的两个桶</em>：
  先加点数、再乘比例，合成一个桶就是 (20+5)×1.2 与 20+5+2.4 的差别
- **暴击两条通道 2026-09-30 起有落点了**（`CritRules`，口径由 klze 定）：面板暴击率 =
  **基线 5% + `channel.crit_chance`**，暴伤倍率 = **基线 130% + `channel.crit_damage`（无上限）**。
  **暴击率超过 100% 不是夹住，而是每满 100% 多一次必定暴击**：105% = 必定一次 + 5% 再来一次，
  240% = 必定两次 + 40% 第三次；每次暴击<em>各乘一遍</em>倍率（105% 全中就是 ×1.69）。
  负增量最多把面板压到 0、把倍率压到 0（不会变成负伤害）。
  **原版那套跳跃暴击被关掉了**（`CriticalHitEvent` 判 `DENY`，粒子与音效一起停），
  引擎是唯一的暴击来源——不关就会与我们的乘区叠成双暴击。一条可观察的连带：横扫的前提是
  "这一发不是暴击"，关掉跳跃暴击后原本会暴击的那几刀改为<em>可能触发横扫</em>。
- **`lifesteal` 自 2026-10-03 起有落点**（`Lifesteal`）：攻击者回复 = **比例 × 真的落到目标身上那个数**。
  四条读法：① 基数跟着<em>最终值</em>走，与 `damage_dealt` 同一条律——被对面免疫成 0 的那发不算伤害，
  也就不算吸血；② 自家 `damage`/`reflect` 补出去的那一发<em>也算落到身上</em>，所以也吸
  （把引擎自伤排除在触发器之外只是为了断递归，回复不产生事件）；③ 比例没有上限，
  那是内容侧的数值决定，越过生命上限的部分由原版 `heal` 自己夹住，引擎没再夹一层；
  ④ 负数比例夹在 0，绝不让"吸血"变成"打自己"。
- **`armor_pierce` 自 2026-10-03 起有落点**（`ArmourPiercing` + `TargetStates`）：它<em>不改伤害公式</em>，
  只在原版算护甲<em>之前</em>把该无视的那部分借走、算完立刻还——曲线仍然只由原版算一次。
  借的是 `ARMOR`，不动 `ARMOR_TOUGHNESS`（卡面说的是"无视护甲"，韧性管的是高护甲段的衰减形状）。
- **还没有落点的**：`physical_damage`、`resistance`
  （`direction_bonus` 与 `backstab_bonus` 已于 2026-09-30 落地，`armor_pierce`／`lifesteal`
  于 2026-10-03，`base_damage` 与 `max_health_scale` 同日走属性投影）
- **独立相乘桶**（卡面写"额外乘区"）：`max_health_scale`——桶内仍加算，桶本身与主桶相乘
  （2026-10-03 起真的作用到属性上：`ADDITION` 的点数先加、`MULTIPLY_TOTAL` 的比例后乘）
- 通道值恒为**增量**（`+15%` 写 `0.15`），不是乘数

### 叠层参数（`stack.<id>.<参数>` 的第三段）

`cap` · `duration` · `gain`。`<id>` 由内容声明，引擎只校验参数名合法；
**引用一个没人声明过的叠层 = 加载错误**。

## 三、条件与动作

### 叶子条件（`when` 数组的元素，2026-09-27 起可以写成树）

四种形态共用一个结构：数值（`{"hp_below": 0.3}`）、枚举（`{"angle": "front"}`）、
开关（`{"charge_active": true}`）、引用（`{"stacks": {"id": "barrier", "at_least": 3}}`）。

| 键 | 写法 | 判的是谁 |
| --- | --- | --- |
| `hp_below` `hp_above` | 小数（0.3 = 30%） | 自己生命 |
| `target_hp_below` | 小数 | 目标生命（斩杀线用） |
| `still_seconds` | 秒 | 自己连续不动的时长（隐含"没在动"） |
| `charge_seconds` | 秒 | 本次蓄力已积累时长 |
| `distance_within` | 格数 | 与目标的距离 ≤ n |
| `light_below` | 0–15 | 所处光照等级 < n |
| `noise_below` | 小数 | 发声量 < n（蹲下不发声这条线） |
| `back_sector` | 角度 | 离目标**背面中线** ≤ n°（《00》背后 120° = ±60°） |
| `angle` | `front` / `front_side` / `all` | 入射角档（与 `back_sector` 同一条定义的两半） |
| `target_state` | `controlled` / `attracted_elsewhere` / `blind` | 目标状态 |
| `target_kind` | `normal` / `elite` / `boss` / `player` | 目标类别（处决只打普通敌人） |
| `moving` `blocking` `charge_active` `parry` `fatal` `appeared_outside_view` | `true` / `false` | 自己这一瞬间在做什么；`fatal` = 这一发会打死我 |
| `stacks` | `{"id", "at_least"}` | 某个叠层当前层数 |
| `count` | `{"on", "at_least"}` | 某个事件本局累计次数 |
| `unseen` | `true` / `false` | **具名条件**，见下 |

`unseen`（未察觉）在卡表里被当**一个**词用，所以只展开一次，全卡表共用：
「背后 120° 内」**或**「目标被其他单位吸引 / 被控制 / 失明」**或**「自己刚从它视野外出现」，
满足任意一条即可（《00》L1016）。要"必须未察觉"就写 `{"unseen": true}`。

### 哪些条件现在真能在游戏里判（2026-09-29 更新）

判定读的是事实快照，事实由 `DamageContact` 从真实命中折出来。**现在能真判的**：
自己/对面的血量线、是否致命、入射角（`back_sector` / `angle` / 背后扇区）、距离、光照、
在移动、**连续静止多久**（`still_seconds`，2026-09-29 起，定义见上面第三节）、蹲下、正在格挡、**目标类别 `target_kind`**（2026-09-28 修了一处取错对象：它判的是
<em>对面</em>那位，早先取的是持卡人自己，于是玩家持卡恒读到 `player`——"只打普通敌人"那类卡
永远不响、"对玩家生效"那类永远响，GameTest `killingANormalTargetChainsOntoANeighbour` 钉住）。
`target_kind` 今天只分得出 `player` 与 ender dragon（→`boss`），其余一律 `normal`；
**还判不了的**（原版没有现成来源，先留默认值，不猜）：
发声量（要潜行/噪声系统）、"刚从视野外出现"、目标"被吸引 / 被控制"（要索敌与控制状态系统）、
精英与 boss 归类（要内容侧给怪打标）。这几条今天恒不成立——是安全方向（只会让卡"没触发"，
不会让它"错触发"）。

**没有对面的那些事件上（`tick`、以及伤害来自非活体的 `damage_taken`），`target_kind` 会读到
`normal`、对面血量读到满格**——那不是"引擎认定它是普通怪"，而是这项事实无从谈起。
所以按目标写的条件不要挂在 `tick` 上。

因此写卡时注意这两条（2026-09-30 纠正过一次，别照旧文档写）：

- **`channel.direction_bonus`＝方向卡那一族（燎原/惊雷/寒霜，即火/雷/冰流派）带来的最外层加法**，
  按《00》公式 `… ×（1+专属buff）＋ 方向增伤` 加在最后、算的是"基础数值 × 那个率"，
  默认封顶 120%（`uncapped`/超限类才突破）。它**与"从哪个方向打"完全无关**。
- **要"背后才算"就写 `channel.backstab_bonus`**（《02》"背刺：背后 120° 攻击额外一次 30%"）。
  它同样加在最外层，但只有这一发的接触落在目标背后 120° 扇区内才加；不成立时留痕会写
  「背刺增伤 0.3 未生效（这一发的接触不在目标背后扇区内）」，不会静默。
  ⚠ 一处已知偏差等确认：正本说背刺是"额外一次**独立伤害**"，我们目前是**并进这一发的最外层加法**
  ——因为原版无敌帧会把同一目标同一刻的第二发整个吃掉（伤害 ≤ 上一发时直接不结算），
  做成真正独立的一发在 1.20.1 上需要给自家伤害类型加 `BYPASSES_COOLDOWN`（这条本来就挂着等裁定）。
  两点差别：并进这一发 ⇒ 这 30% 不再单独过一次护甲与减免，也不会被无敌帧吞。

### 组合子（把条件拼成树）

| 写法 | 含义 |
| --- | --- |
| `{"all_of": [ … ]}` | 全部成立（`when` 数组本身就是这个意思，通常不用显式写） |
| `{"any_of": [ … ]}` | 任意一条成立 |
| `{"not": { … }}` | 取反 |
| `{"if": { … }, "then": { … }, "else": { … }}` | 条件分支（`else` 可省；省了就是门槛不过→整体不过，不猜默认值） |
| `{"k_of_n": 2, "of": [ … ]}` | n 条里成立 k 条 |
| `{"sequence": [ … ], "cursor": "combo_step"}` | **按顺序轮转**：这一次只看指针指的那一条 |

两条纪律：

- **轮转的指针不在条件里**，它是"这个玩家在这张卡上走到第几步"，归持久账本（`CounterStore`，
  键 `trigger.cursor.<id>`）所有，所以"跨攻击不重置"天然成立，循环 = 同一条取模之后的样子，
  不另开一种写法。**推进时机只有一种读法**：整条 `when` 成立之后才 +1（过不去就停在同一步）。
  卡表里目前还没有卡用轮转，所以这条按唯一自洽的读法定下；若其实想要"每次派动都推进"，说一声再改。
- **嵌套深度上限 6 层**，超了报加载错误。写歪了的条件（未知键、一个对象里两个组合子、
  `k` 超出条数、`sequence` 没给 `cursor`）一律是错误，绝不"未知即放行"或静默丢掉。

判定不读游戏世界，读的是换算好的事实快照（`Facts`），因此每条判据都能在 `logicTest` 里断言——
包括"到底是哪一条门放行的"这句归因（守方管线的免疫否决必须引用它）。

这些键在世界侧的**出处**分三等，写卡前照这张表挑：

- **已经接通的**：血量线（自己/对面）、`fatal`、`moving`、`blocking`、`sneaking`、
  `distance_within`、`light_below`、`back_sector` / `angle` / `target_kind`、
  **`stacks`（层数）**、**`count`（本局累计次数）**、**`sequence` 的轮转指针**——
  后两档 2026-09-28 起由执行器在评测之前把账本贴进快照（`Facts.withLedger`），
  所以"叠满 3 层才怎样""本局第三次弹反才怎样""走到轮转第 2 步才怎样"在世界里真的会翻脸。
  贴的口径钉死三条，写卡前要认：
  1. **计数把"这一次"也算进去**——`at_least: 3` 从<em>第三次</em>派动开始成立，不是等到第四次
     （反过来"先判后加"会整体晚一次，方向是"该响没响"，已被断言钉住）。
  2. **"本局"＝服务端进程里这本账活着的时候**：与世界重启同步清零、<em>不写存档</em>
     （与周期起点 `CardCadence` 同一口径）。要"跨重启仍累计"得另做持久化，那是新需求。
  3. **轮转指针只在整条 `when` 成立时推进一格**；过不去就一直停在同一步，转满一轮取模回到第 1 步。
     指针与层数是分开的两本账（`trigger.cursor.<id>` vs 叠层裸 id），互不覆盖。
  另外 `count.on` 现在按<em>已注册事件</em>校验：写一个不存在的事件名是加载错误，不再"永远不响"。
  引擎自有的 `trigger.*` 资源（冷却、已开的强制精准窗口）不算叠层，不贴进 `stacks`。
- **静止这一族也接通了**（2026-09-29）：`still_seconds` 与 `moving` 读的是同一份位置采样
  （`core/effect/Stillness` + `common/player/PlayerStillness`，每 tick 末尾采一帧）。四条口径：
  1. **"动"的定义是位置变了**，不是速度非零——坠落、被推、水里漂都算在动；这也让
     `{"still_seconds": n}`（它要求"没在动"且时长够）不可能自相矛盾。
  2. 阈值是**平方距离 1e-6 格²**（≈每 tick 0.001 格）。采样<em>保留旧锚点</em>，所以每 tick 挪一点点
     的漂移会在约 1100 tick 后累计越界被判成"动了"——逐 tick 刷新坐标的写法会被漂移永久骗成站定。
  3. **第一次看见一个人 = 静止 0 秒 + 没在动**（读操作不写状态）。不是"知道他站着"，是还没采过样。
  4. 动了之后，"在动"这个读数<em>保持一整个 tick</em>：采样把锚点搬到新坐标之后，如果只比坐标，
     同一 tick 里稍后才到的那次命中会读成"没动"，`{"moving": true}` 那类卡会整 tick 漏触发。
  顺带：`stand_still` <b>事件</b>现在只差"什么时候算站定"这一个定义了（数据已经都在），
  要派发请给一句阈值口径（比如"从动到静的那一刻响一次"）。
- **还没有出处的**（结构上恒不成立：写上去不报错，但也永远不会响）：
  `charge_seconds` / `charge_active`（蓄力运行时，等输入通道裁定）、
  `{"parry": true}`（"刚刚弹反成功"这<em>一个开关</em>；`parry_success` <b>事件</b>是通的，
  两者不是同一件事，别混着写）、`target_state`（被吸引 / 被控制 / 失明）、`noise_below`、
  `appeared_outside_view`。
- **只接通了一部分的**：`unseen` 是三条的<em>或</em>，今天只靠"背后 120° 内"这一条成立
  （另两条没出处）。门槛方向是安全的（该过的仍然过），但等控制/视野接上之后同一张卡的
  `unseen` 会开始<em>更容易</em>成立——那时数值要重校。

取值集合（`target_kind` / `target_state`）如果要加新的，请点名。

### 已注册动作（结构校验严格，语义在 M2 执行）

`stacks`（加/减层数，可 `ignore_cap`）· `damage`（`basis`: armor/attack/incoming/const + 系数 + 半径）·
`knockback` · `stun` · `launch`（落地追伤比例）· `slow` · `reflect` · `extra_resolve`（可 `unbounded`）·
`copy_attack` · `crit`（把<em>下一次攻击</em>武装成必暴）· `lethal_immunity` ·
`force_parry`（一律按精准结算）· `ignore_armor` · `interrupt`

### 动作字段一览（写卡照这张表，别的名字加载期就报错）

| 动作 | 允许的字段 | 必填 |
| --- | --- | --- |
| `stacks` | `id` · `amount` · `ignore_cap` · `consume` | `id` |
| `damage` | `basis` · `coefficient` · `radius` · `radius_per_stack` | `basis` · `coefficient` |
| `knockback` | `strength` · `radius` | `strength` |
| `stun` | `seconds` · `radius` | `seconds` |
| `launch` | `landing_ratio` | `landing_ratio` |
| `slow` | `percent` · `seconds` · `radius` | `percent` · `seconds` |
| `reflect` | `ratio` · `basis` | `ratio` |
| `extra_resolve` | `count` · `unbounded` · `radius` | — |
| `copy_attack` | `radius` | `radius` |
| `crit` | `chance` · `damage` · `seconds` · `count` | — |
| `lethal_immunity` | `uses` · `cooldown` | — |
| `force_parry` | `seconds` | `seconds` |
| `ignore_armor` | `ratio` | `ratio` |
| `interrupt` | `seconds` · `radius` | `seconds` |

四个高频写错的位置，钉在这里：

- 伤害的比例字段叫 **`coefficient`**（`ratio` 只有 `reflect`/`ignore_armor` 用）。
- 必定暴击写 **`{"crit": {}}`**（`chance` 不写就是 +100%，没有 `guaranteed` 也没有 `always`——
  旧词表里那个 `guaranteed` 与 `chance` 是同一件事的两种写法，2026-09-30 收掉了）。
- **`crit` 的 `seconds` 是"没打出去就失效"那条线，不是 buff 的持续时长**：每次真落地只扣一枚，
  所以 `{seconds: 3}` 是"3 秒内的下一击"，"接下来 3 击"要写 `{count: 3}`（两者可以一起写）。
- 击飞落地追伤写 **`landing_ratio`**（`launch` 没有 `follow_up`/嵌套动作）。

动作对象一律是 `{"动作名": {字段…}}` 的单键形态，`type` 只出现在四类子句上。

`damage.basis` 只认 `armor`（持卡人的护甲**属性**，不是装备栏点数）· `attack`（攻击力）·
`incoming`（这一发的量）· `const`（系数本身就是数值）四种，写别的直接加载错误。
`radius_per_stack` 今天还没有归属（半径随哪条叠层涨没定），写了会被报出来而不是按 0 算。

### 每层多少的两种写法（今天折出来必须同一个数）

- `stacks` 子句里的 `per_stack: [{target, value}]` —— 层数就是这条资源自己，所以这里
  **不允许**再写 `source`/`uncapped`（写了是加载错误）。
- 顶层 `mechanic_modifier` + `source: {counter: <叠层 id>, per_layer: <每层多少>}` ——
  用于"读另一条叠层的层数"。

两条路都进同一个折叠表（`EffectHost.foldModifiers`），断言钉着；只实现一条会让卡面写了
`per_stack` 却静默不生效——那是最难查的一类假绿。

**这十四种里目前有八种真的作用到游戏里**：`lethal_immunity`（致命免疫：判定说"这一发会打死我"
→ 守方管线第①步打成 0 → 用掉的次数进冷却）、`stacks`（加 / 扣层数，受声明上限夹住，
`ignore_cap` 才允许越过，`consume: true` 是扣层而不是加负数）、`damage`（**独立伤害**＝
基数 × 系数，`basis` 只认 `armor` / `attack` / `incoming` / `const` 四种，写别的直接加载错误；
`radius` 是以持卡人为圆心的半径格数）、`knockback`（推开目标，同样支持 `radius`）、
`reflect`（把这发的一个比例<em>还给打我的那位</em>，基数默认 `incoming`，不搜半径）、
`force_parry`（接下来 N 秒内的格挡一律按精准算）、`crit`（把<em>下一次攻击</em>武装成必暴，见下）、
`slow`（让目标慢下来若干秒，见下）。

`crit` 的读法（klze 2026-09-30："下一次攻击可以视为有条件的临时 Buff，给个攻击就消失的 100%
暴击率效果就行"）——六条，每条都有断言钉着：

- **它是加进面板的那一格，不是替换面板**：`chance` 不写＝`1.0`，与基线 5% 相加得 105%，于是
  溢出那条规则照旧生效（"必定一次 + 5% 再来一次"）。`damage` 同理，加在<em>单次</em>暴伤上。
  做成"武装了就正好暴一次"是最容易写错的那版实现，它会让面板上的暴伤词条静默失效。
- **绑在哪个事件上就决定它是"此击"还是"下一击"**：`attack` 由 `Player#attack` 的<em>第一行</em>发出，
  同一刀的伤害事件在后面才发生（源码 1089 与 1142 行，这个顺序就是这条读法的全部依据），所以绑
  `attack` ＝ 这一击必暴（重武池那种"此击暴伤 +20%"）；绑 `hit`／`damage_taken`／`parry_success`
  ＝ 下一击（弹反池那种）。引擎没有为此再加一个"作用范围"字段。**判据其实不是事件名字，而是"它发在同一击的伤害之前还是之后"**——
因此给还没派发的 `charge_release` 留一句接口约束：重武池那种"此击暴伤 +20%"要能表达，派发点必须排在
同一击的伤害事件<em>之前</em>（与 `attack` 同侧），否则那张卡会静默变成"下一击"。
- **每次真落地只扣一枚**（`count`，不写＝1）：所以 `seconds` 只是<em>失效线</em>，不是"这段时间刀刀必暴"。
  攒的上限就是卡面写的 `count`，满了再触发<em>既不续命也不加发数</em>（每枚各计自己的到期，与
  `stacks` 同一律）。多张卡各自武装则各加一遍数值——那是 Buff 叠加；同一张卡的子句里写两遍
  `crit` 也只加一遍（一张卡一份账）。
- **谁算"一次攻击"**：这一发<em>进了结算</em>（`LivingDamageEvent`）就扣一枚。所以被盾整个挡下的
  那一发不扣（它走不到结算，与 `hit` 同一口径）；自家 `damage`/`reflect` 补出去的那一发同样不扣
  ——否则一次弹反就把玩家攒着的必暴用掉了。
- **卡面写"必暴"不会被"不判定"那条入口吞掉**：纯推演与测试态走 `NO_ROLL`（整格跳过），但这一发身上
  有武装时改按 `GUARANTEED_ONLY`——只补"必定那一部分"，概率那一次仍不赌。少了这条，武装会被扣掉
  而数值一点不变（账动了、数没动），是最难查的那种静默。
- 时长与在途都走 `CounterStore`（与 `force_parry` 同一形状，键名 `trigger.<卡 id>.crit`），
  数值出处只有卡面那三个字段，账本里不存第二份。

示例卡两张：**「灰守」**（`ash_guard`）在 `damage_taken` 上挂 `{"crit": {"seconds": 3.0}}`——挨一发之后
三秒内的<em>下一刀</em>必暴，GameTest `anArmedCritBurnsOnTheNextLandedSwing` 走完整生命周期；
**「毒刃」**（`venom_edge`）在 `attack` 上挂 `{"crit": {}}`——出手即<em>这一击</em>必暴，
GameTest `critArmedOnAttackFeedsThatSameSwing`。

`slow` 的读法（2026-10-03 起有执行器）——四条：

- **数值就是卡面那个百分比**：`percent: 0.3` ⇒ 目标移速乘 `0.7`（一条 `MULTIPLY_TOTAL` 的
  `−0.3` 修正）。越界夹在 0~1（1.5 不是"倒着走"，负数不是"加速"），算式在 `Slowness`。
- **为什么不注册一条原版 `MobEffect`**：注册效果时属性修正的<em>量</em>钉死在效果定义里，
  之后只能靠 `amplifier` 取档（原版算法是 `amount × (amplifier + 1)`，
  源码 `MobEffect#getAttributeModifierValue`），于是卡面写 30% 还是 22% 都得就近取整到级
  ——那是第二个真相。我们直接挂一条带稳定 UUID 的 transient 修正。
- **一张卡对一个人只有一条**：UUID 由卡 id 派生，再触发只是<em>刷新</em>时长；
  多张卡的减速各挂各的（这才叫不同来源）。半径 0 = 只缠直接目标，写了半径就以持卡人为圆心搜。
- **到期靠服务端 tick 摘，且不写存档**：与层数、`crit` 武装同一条律（补十七）。漏摘就是一条
  永久 debuff，所以 GameTest 直接把表拨过 40 tick 再验属性回到原值。

示例卡「墓华」（`grave_bloom`）在 `damage_dealt` 上挂 `{"slow":{"percent":0.3,"seconds":2.0}}`，
GameTest `slowTakesTheLegsOffWhoActuallyGotHit` 验"作用在被打中的人身上 + 到期摘干净"。

`armor_pierce` 那条通道解决的是"这个人<em>每一发</em>都无视 X% 护甲"。<b>动作 `ignore_armor`
仍然没有执行器</b>，因为它的语义有两条互斥的读法，需要一句裁定：① "接下来几发无视护甲"
——那就与 `crit` 同一个形状（绑 `attack` 是此击、绑 `hit` 是下一击，加 `count`/`seconds`）；
② 正本《00》里"处决不结算护甲与减伤"那种<em>穿透声明</em>——那是 `AttackPipeline.Penetration`
的位置，槽位已经有，但目前只能由引擎内部声明，没有卡面通道写它。
写 `{"ignore_armor": {...}}` 现在会照实在日志报一条"没有执行器"，不会静默。

`force_parry` 有一条读法要先说清：被它强制的那一下**照发 `parry_success`**——"一律按精准结算"要的
就是让那 N 秒里所有"弹反成功后"的收益都吃得到；只改判定名字而不发事件，这条动作等于没做。
《挂点覆盖表》把它列为"待内容侧确认"，代码先按这个唯一自洽的读法实现，并有 GameTest 钉住
（`forcedParryWindowMakesLateBlocksCountAsPrecise`，它同时钉住另一件事：**先举盾挡住的那一发拿不到
`damage_taken`**，因为原版把挡下的伤害整个取消了）。

**通道落点分三类**：`armor` / `max_health` / `max_health_scale` / `base_damage` / `move_speed` /
`attack_speed` 已经真的挂到玩家属性上
（`CardAttributes`，按通道派生的稳定 UUID 换、幂等、点值走 ADDITION 比值走 MULTIPLY_TOTAL，
上限降下来当场夹血）；`all_damage` / `melee_damage` / `direction_bonus` / `backstab_bonus` /
`damage_reduction` 走自定义结算管线（前四条在攻方，最后一条在守方）；
**`crit_chance` / `crit_damage` 自 2026-09-30 起也有落点**（`CritRules`，见上面"暴击两条通道"那段）；
**`lifesteal` 自 2026-10-03 起有落点**（`Lifesteal`：回复 = 比例 × 落到目标身上的最终值）；
**`armor_pierce` 同日有落点**（`ArmourPiercing`：在原版算护甲之前把那部分借走、算完还回去）。
**还没有落点的**只剩两条：`physical_damage`、`resistance` —— 写上去不会报错，但今天不产生任何效果。
它们要的都是<em>伤害分类</em>（物理/法术、火/冰/雷那张抗性表），原版没有这个维度，
要么内容侧定口径、要么由自定义管线补一张分类表。

**能被叫醒的事件今天是八个**（2026-09-28）：

| 事件 | 什么时候响 |
| --- | --- |
| `attack` | 我出手的这一下（挥出去就算：被无敌帧吃掉、被打成 0 都算） |
| `hit` | 我打中的这一下（排在结算之后，攒的东西给下一发用） |
| `damage_dealt` | 我这一发<em>真的</em>造成了伤害（基数装结算后的最终值） |
| `kill` | 我把对面打死了（`target_kind` 判的就是对面那位） |
| `damage_taken` | 我挨的这一下（守方管线走完之后） |
| `block_success` | 我举盾挡下了这一下，但没卡在窗口里 |
| `parry_success` | 我举盾挡下了这一下，且举盾时长落在窗口内（精准格挡） |
| `tick` | 周期到点（配合 `every`，见下） |

攻方那四条的分工必须写清，因为会有卡各写一条：

1. **`attack` 看动作，另外三条看结果。** 原版在 `Player#attack` 的<em>第一行</em>就发
   `AttackEntityEvent`（源码核过：`ForgeHooks#onPlayerAttackTarget`），所以一刀哪怕最后一点伤害
   都没落地，"出手"照样记。GameTest `swingsAreCountedEvenWhenTheBladeDoesNotLand` 专门用
   "必然致命、必然被免疫"的受害者把 `attack` 与 `damage_dealt` 劈开：同一刀，毒照叠、花不开。
2. **`damage_dealt` 的基数是最终值，`hit` 的基数是进管线的那个数。**"造成伤害时补一发 25%"
   要的是前者；被对面免疫成 0 的那发根本不发 `damage_dealt`。
3. **引擎自己补的那一发不再叫醒攻方事件**（`attack` / `hit` / `damage_dealt`），否则
   `damage` → `damage_dealt` → `damage` 会一路递归到栈溢出。`kill` 不在其列：打死就是打死了，
   死的实体不会再死一次。
4. **`kill` 只能挂在 `LivingDeathEvent` 上。** 1.20.1 的 Forge<em>没有</em> `LivingDiedEvent`
   这个类（源码核过），而 `LivingDeathEvent` 是可取消的——若别的模组取消了这次死亡，
   我们的 `kill` 已经响过一次。这条偏差记在进度文档，不做"看起来更准"的修补。

`attack` 与 `kill` 上<em>没有</em>"这一发的量"（出手那刻数还没打出来，击杀那发早结算完了），
所以基数只有 `armor` / `attack` / `const` 三种真能用；写 `basis: incoming` 会照实报
"基数 这一发的量 × 系数 = 0"，不静默。同理，这两条事件上没有"打我的那位"，
`reflect` 在这里天然没有对象；而半径 0 的 `damage` / `knockback` 在没有对面的事件上
会被<em>报出来并跳过</em>（原先这条路直接把服务器打抛，见 GameTest
`actionsNeedingATargetAreReportedWhenThereIsNone`）。

`tick` 只和 `"every": <秒>` 一起用（`{"type":"trigger","on":"tick","every":30.0,…}`）：
每 30 秒兑现一次。三条读法钉在 `CardCadence` 里——**起算点是引擎第一次看见这张卡的那一 tick**
（服务器重启会重新起算）；**错过的那些不追补**（卡了 3 秒不会把一次触发变成三次）；
同一 tick 里多个周期按卡 id 顺序跑。

`block_success` 与 `parry_success` 挂在原版的 `ShieldBlockEvent` 上，**"算不算挡住"由原版判**（正面半球来的、
没被 `BYPASSES_SHIELD` 绕过、不是穿刺箭的第二段），我们不重述它的规则，只往上加一条时机判定。
三道闸门写卡前要看清：

1. **必须在挡**，而原版要求举盾满 5 tick 才算在挡 ⇒ "窗口 ≤ 0.25 秒 = 5 tick"的写法
   <em>结构上永远不精准</em>，那是死区不是配置项（这条已被断言钉住）。
2. **没挡住就不响**：从背后挨的那一刀、穿盾的法系伤害都不会发这两个事件
   （GameTest 里"背后那一发没攒到层"就是专门验它的）。
3. **必须被授予过 `parry` 能力**（`{"type":"mechanic","id":"parry","base_window":0.4,…}`）：
   没这能力两个事件都不发——挡下近战是原版一直在做的事，不是一张卡的触发器。

这三道闸门<em>之前</em>还有一件全局的事：**盾到底挡掉多少是 `manifest.json` 里 `combat.block_reduction`
那个数**（klze 2026-09-30 裁定"先随便填个数，到游戏里改 JSON 试手感"）。出厂 **1.0 = 与原版一样
整个取消**，所以今天谁的手感都没动；写 0.2 就是"取消两成、其余照常走护甲与减免"。四条读法：

- 它是**全局战斗口径**，一张卡都没戴的人举盾也按这个数——所以它在闸门之前写回事件，不属于任何卡。
- 它改的是**"取消掉多少"**，不是减伤通道：原版是 `剩下的 = 原始伤害 − 挡下的`，剩下的那部分还要
  过一次护甲。而**盾的磨损不看它**（原版按原始那一发算 `1 + floor(伤害)`），调小它不会把盾改脆。
- 挡不完之后 `damage_taken` 第一次会在"举盾挡住了"的场合响（以前完全挡下的那发根本走不到伤害事件），
  但**弹反/格挡奖励的基数仍是原始那一发**，不跟着这个数缩。
- 这个数写错**不会静默**：`1.5`、`"0.5"`（带引号）、键名拼错都会被 `Manifest.validate` 报成一条错误、
  整次 reload 保留上一版。要防的是 DFU 那个陷阱——`optionalFieldOf(name, default)` 底下的
  `OptionalFieldCodec#decode` 在子 codec 失败时返回 `success(Optional.empty())`，越界值与"没写这行"
  在 codec 眼里是同一件事（本项目第三次命中同类，前两次见《加载期会硬报错的情况》）。

GameTest `theBlockNumbersayshowmuchtheshieldcancels`（1.0/0.5/0.0 → 掉血 0/2/4，盾损耗恒为 15）。

其余七个事件名（`parry_fail`、`charge_release`、`charge_interrupt`、`stand_still`、
`shield_down`、`control_immune`、`skill_cast`）解析与校验都通过，但**还没有人发它们**——
写在这些事件上的卡现在不会响。前六个各缺一个世界侧来源（`parry_fail` 要"举盾了但没挡住"这个
判据、`stand_still` 与 `shield_down` 要持续状态机、`control_immune` 要控制效果系统）；
`charge_*` 缺"怎么开始蓄力"的输入通道（玩法决定，见交付文档），`skill_cast` 等技能栏落地。

两条会直接影响卡面数字的事实：

- **独立伤害是"另一整发"，不是把原来那个数改大**。它会完整地再过一次两条管线：攻方的全伤等乘区
  照乘（《00》要的"以护甲值为基数的<em>完整乘区</em>"正是这个意思），守方的护甲与减免照算。
  但它<em>不并进</em>原来那一发的数里——所以同一个乘区对同一发数字只生效一次，
  两发各算一遍，不会出现"减伤被暴击又放大一次"那种串。想要"以这一发为基数"就写 `basis: incoming`。
- **独立伤害绕过原版无敌帧**（2026-09-30 起，klze 裁定"让本 mod 的所有伤害无视无敌帧"）。
  以前同一刻打到同一目标的第二发会被原版整个吞掉（`invulnerableTime > 10` 且伤害 ≤ 上一发就
  直接不结算），所以"冲击波"对刚被那一刀砍中的目标不叠加；现在自家的杀伤类型
  `nextcard:card_extra` 挂在 `bypasses_cooldown` 标签里，第二发真的落下。
  一条实现上的硬事实值得记着：**代码里 `new Holder.Direct<>(…)` 造的杀伤类型挂不上任何标签**
  （`Holder.Direct#is(TagKey)` 是硬写死的 `false`），所以这个 damage_type 必须是数据包注册的
  （`data/nextcard/damage_type/card_extra.json` + `data/minecraft/tags/damage_type/bypasses_cooldown.json`）。
  GameTest `engineDamageIgnoresTheInvulnerabilityWindow` 两头都断言：标签在注册表里查得到、
  同 tick 两发各掉 3 点。

**没执行器的动作会报出来，不会静默跳过**：日志一条 warn（同一句只报一次），GameTest 里也有断言。
所以"这张卡没效果"如果是引擎缺执行器，你们能从日志里读到，不用猜。

`lethal_immunity` 的 `uses` / `cooldown` 读法只有一种：**每次免疫放一枚"在途"计数，各计自己的冷却，
在途数达到 `uses` 才拦住**。所以 `{"uses": 1, "cooldown": 20}` = "免疫一次，20 秒内不再免疫"；
`{"uses": 2, "cooldown": 30}` = "最多同时存两次，每次用完各计 30 秒"。
另外**不致命的挨打一律不动账本**（引擎在扣账之前先判致命，避免"该活下来时没免疫"）。

引擎自有的资源用 `trigger.` 前缀记账（冷却、窗口），**内容声明的叠层 id 不许用这个前缀**——
加载期直接报错，否则"壁障"和"免疫冷却"会记在同一本账上。

## 四、两个池怎么落到语汇上（示例）

### 盾反：时机感知（窗口 +30%）+ 壁障（层数资源）

```json
{
  "tier": 1, "card_class": "B", "tags": ["nextcard:block"],
  "effects": [
    { "type": "mechanic", "id": "parry", "base_window": 0.4, "ordinary_reduction": 0.2 },
    { "type": "mechanic_modifier", "target": "window.length", "value": 0.3 },
    { "type": "mechanic_modifier", "target": "channel.move_speed", "value": 0.10 },
    { "type": "stacks", "id": "barrier", "scope": "persistent", "cap": 3, "duration": 6.0,
      "gain": [ { "on": "block_success", "amount": 1 } ],
      "per_stack": [ { "target": "channel.damage_reduction", "value": 0.03 },
                     { "target": "channel.damage_reduction", "value": 0.04,
                       "when": [ { "angle": "front" } ] } ] }
  ]
}
```

窗口算法（`WindowMath`）：
`窗口 = 基础 ×（1 + Σ延长项）× Π乘区 ÷ Π难度`
→ 时机感知 + 节奏记忆 + 绝境读秒 + 反射神经 = `0.4 × (1+0.3+0.5) × 2 ÷ 3`。

角度档（`block.angle`）与"格挡不再受角度限制"共用同一槽位，只是取最宽档：

```json
{ "type": "mechanic_modifier", "target": "block.angle", "value": "all" }
```

### 蓄力：招式卡（给上限）与辅助卡（改规则）

```json
// 招式卡（过肩劈）：声明并授予机制 + 自己的蓄力点
{ "type": "mechanic", "id": "charge", "bar_max": 2.0 },
{ "type": "trigger", "on": "charge_release", "at": 2.0,
  "actions": [ { "crit": { "chance": 0.2 } }, { "stun": { "seconds": 1.5 } } ] },
{ "type": "mechanic_modifier", "target": "channel.melee_damage", "value": 0.10 }

// 辅助卡（沉肩）：只改规则，不提供蓄力条
{ "type": "mechanic_modifier", "target": "charge.rate", "value": 0.30 }

// 辅助卡（开山）：+2 秒上限 + 5 秒档的招式
{ "type": "mechanic_modifier", "target": "charge.bar_bonus", "value": 2.0 },
{ "type": "trigger", "on": "charge_release", "at": 5.0,
  "actions": [ { "ignore_armor": { "ratio": 0.5 } }, { "knockback": { "strength": 1.0, "radius": 4 } } ] }
```

蓄力表（`ChargeTable`）：上限 = 声明值取最高 + 加成加算（3 + 2 = 5 秒）；
时刻 t 生效的招式 = "`at` ≤ t 的最高档"（同档多张卡一起触发），声明 `inherits` 的档把下面一档一并带出
（3 秒档"保留 2 秒那一档的加成"）；超过上限的部分每段转 1 层「过量蓄势」。

## 五、加载期会硬报错的情况（fail-fast，绝无静默）

1. 未知子句类型 / 未知事件 / 未知槽位 / 未知机制 / 未知动作 / 未知条件
2. 子句、动作、条件里出现当前类型不认识的键（带上下文，如 `action stun: unknown key meters`）
3. 改写一个**没有卡声明过**的机制（`charge.*` 无 `mechanic: charge`）
4. 引用一个**不存在**的叠层（`stack.ghost.cap`、动作 `stacks.id`、条件 `stacks.id`、每层来源 `counter`）
5. 同一个叠层被声明成两种 `scope`；语义唯一的槽位出现两个不同值
6. 在非上限类槽位上写 `uncapped`；同时写 `value` 与 `uncapped`；枚举槽位（`block.angle`）写数字或写错档位
7. 叠层 id 不合规范（须匹配 `[a-z0-9_.-]+`）；`at` 绑在非 `charge_release` 事件上
8. `manifest.json`：**写了就必须合法**——未知键名、越界数、类型写错（`"0.5"` 带引号）一律报错；
   <b>缺席</b>则分两种：整包内容是空的（卡数 0）时缺席合法、用出厂默认值（铁律一：删光
   `data/nextcard/` 引擎照跑），<b>有卡却没这份文件</b>才是错误（文件名写错或漏打包）。
   缺席与写坏都<em>不</em>许悄悄落回默认值而不吭声。这一条不是 codec 给的——
   `optionalFieldOf(name, default)` 会把它们全吞成"这个键没写过"
   （源码 `OptionalFieldCodec#decode`：子 codec 失败时返回 `success(Optional.empty())`），
   所以 `Manifest.read` 在 codec 之外用<em>同一批 codec 对象</em>把每个键再解一遍，
   错了就整次 reload 保留上一版

## 七、内容作者注意事项（会踩的坑）

1. **不要用引擎槽位名当卡文件名**。门 G2 会把每张卡的**文件名**当作内容字面量去扫 `core/`——
   若出现 `cards/charge.json`，`core/Mechanics.java` 里的 `"charge"` 就会被判违规。
   槽位名与机制名（`charge`、`parry`、`barrier`……）属于引擎，卡文件名请避开它们。
2. 槽位 id 用**点号**分隔（`window.length`、`stack.barrier.cap`、`channel.armor`），不要用冒号：
   冒号形式的值会被 G2 当成内容 token 收集。
3. 每张卡仍须满足既有的加载校验：tier 1–5、A 类 tier≥3 且声明体系、C 类 tier≥5、
   标签已注册、`requires` 是可解析的标签、每卡至少一个非判断标签。
4. 改完内容跑 `./gradlew logicTest`：G1（空内容可调用）/ G2（core 无内容字面量）/
   G3（概率性质）/ 内容一致性 / 本词表门。条数不写在这里——最后一行 `pure-logic tests: N passed` 就是。
   世界内的门是 `./gradlew runGameTestServer`。
5. 本机构建需要 Java 21 工具链（MDG 要求），当前用 Trae 自带的 Temurin 21：
   `./gradlew logicTest -Porg.gradle.java.installations.paths="<jdk21 路径>,<jdk17 路径>"`
6. **攒着的运行期状态不跨重启**。写进存档的只有卡账（拥有哪些卡 / 抽了几次 / 体系计数器）；
   而**叠层的层数、`force_parry` 的窗口、`crit` 的武装、`count` 的本局次数都在内存里**，
   服务器一重启就清零，与"周期从引擎第一次看见这张卡那一 tick 起算"是同一口径。
   所以"这次先攒着、下次上线再打出去"这类卡今天会掉——要它跨会话就得先给引擎加一条
   运行期状态的存档契约（那是结构决定，不是给某张卡开后门）。门：
   GameTest `inFlightStateIsNotPartOfTheSaveGame`。

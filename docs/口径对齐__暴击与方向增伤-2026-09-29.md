## 一、暴击：他们是自己算的，不碰原版判定

结论先给：**powerlevel 的暴击 100% 自算，与原版那套"空中跳跃 ×1.5"没有关系**；但他**也没有关掉原版判定**，只是把最终金额整个覆盖掉 ⇒ 结果是**原版暴击的动画与音效照播、数值却不暴击**。这不是他写错，是"覆盖式重算"这条路线自带的错位，我们如果走同一条路必须一起处理。

逐条出处（他的类与行）：

| 环节 | 他的做法 | 位置 |
|---|---|---|
| 概率从哪来 | `crit = spec.forceCrit \|\| (spec.canCrit && random < atk.critChance)`，一次多段攻击只对主段 roll | `core/combat/Damage.java:94`、`:109` |
| 倍率 | `critMul = 1 + atk.critDamage`，作为一个乘区与其他项连乘 | `Damage.java:41-43`、`:67` |
| 哪些不吃暴击 | `canCrit = (axis == MODE)` ⇒ **元素轴伤害一律不暴击**；附加结构（extra specs）一律 `crit=false` | `Damage.java:11`、`:45`、`:113` |
| 数值来源 | 中文键 `暴击率`/`暴击伤害` 累加进 `CombatStats`；**只从卡的 `stats` 合并，没有基础值** ⇒ 没拿暴击卡 = 暴击率 0，玩家永不暴击（除非卡面"必定暴击"） | `CombatStats.java:22-23`、`:113-117`；`StatAggregator.java:23-25` |
| 必定暴击 | `DamageSpec.forceCrit` 由池子按卡名设置 | `DamageSpec.java`、`CombatHooks.java:259-261` |
| 一个玩法开关 | `critRequiresFullCharge`：开启时"这一击的蓄力刻度 < 0.9"（没蓄满/连点）**不许暴击** | `forge/CombatConfig.java:21`、`CombatHooks.java:255-257` |
| 接管点 | 挂 **`LivingHurtEvent`（护甲之前）**，从 `attackDamageOf(player) × 蓄力系数` **重算 base**，最后 `deliver()` 覆盖 `event.setAmount(total)` | `CombatHooks.java:76`、`:247`、`:319-331` |

**与设计文档冲突的一条（别照抄）**：`06-细化全文:6450` 明写"**追加判定也可以暴击，暴击率按你的面板结算**"，他的实现是附加结构一律不暴击。

## 二、暴击：正本已经写死的 / 还没写的

已经写死、不用再讨论的：

- `00:238` 刺客伤害公式：`基础伤害 × 对应系数 ×（1+全伤）×（1+近战分类）×（1+专属buff）× 暴击倍率 × 背刺倍率 + 方向增伤` ⇒ **暴击是一个独立乘区**，与背刺倍率并列相乘，位置在专属buff 之后、最外层加法之前。我们 `AttackPipeline.Step` 的顺序（… OWN_BUFF → SPECIAL_DAMAGE → **CRIT** → DIRECTION …）与它一致。
- `02:196` 与 `02:207-208`：**暴击率/暴击伤害是"便宜词条"**，档位 `+6/+12/+20%`（暴伤 `+10/+20/+35%`），刺客线可 +1 档 ⇒ 语义是**面板加法增量**，可以放开给。
- `04:86` 规范词表里 `暴击率`、`暴击伤害` 是正名（同义词见 `02`）。
- `07:90` 落地难度评估把"暴击"列进乘区清单，并要求"严格按名词表 4.1 实现；**卡面数值不进代码**"。

**正本没写、必须裁定的四条**：

1. **初始暴击率**（玩家一张暴击卡都没有时是多少）。
2. **暴击倍率基线**：`暴击倍率 = 1 + 暴伤加成`，还是有一个基础倍率（原版是 1.5）。
3. **原版跳跃暴击留不留**——留就会与我们的乘区叠成**双暴击**（两个 ×1.5 各来一遍）。
4. **暴击率要不要上限**（正本只给"方向增伤默认封顶 120%"这一条先例）。

## 三、暴击：我们的三条路，推荐 C

- **A 照他做（挪到护甲前重算并覆盖）**。代价太大：我们必须自己重述原版护甲与抗性——现在**故意不算**（接管点在原版算完护甲之后，再算一次就是双倍减免，这条纪律有门钉着），而且会一并带上"动画与数值错位"那个问题。**不推荐**。
- **B 只在原版暴击之上加一层**（`crit_damage` 表示"原版暴击发生时额外乘 (1+X)"）。与原版手感一致，但**"暴击率 +20%"这类卡全部变成空话**（原版暴击率不是数值，只在跳跃攻击时才成立）。**不推荐**。
- **C（推荐）关掉原版，让引擎成为唯一真相**。1.20.1 的 `CriticalHitEvent` **不是 cancelable，而是 `@HasResult`**（源码核过：`ForgeHooks#getCriticalHit` 只在 `result == ALLOW` 或 `vanillaCritical && result == DEFAULT` 时返回事件），并且 `Player#attack` 里的 `flag2` 同时驱动**粒子与音效** ⇒ 我们 `setResult(DENY)` 就能把原版暴击**连动画一起**停掉（`ALLOW` 不用，理由见下面第二条）。之后 `crit_chance` 决定要不要暴击、`crit_damage` 决定倍率。
  - 改动小：一个事件订阅 + 一个"这一 tick 这个玩家是否暴击"的在档标记（与我们已有的 `ParryTiming`、`CardDamageSource` 同一手法），**不需要挪接管点、不需要重算护甲**。
  - **`ALLOW` 不是"必定暴击"的现成开关**（源码核过）：`Player#attack` 拿到事件对象后只做 `f *= hitResult.getDamageModifier()`，而构造时传进来的 `damageModifier` 是 `flag2 ? 1.5F : 1.0F`——没跳跃时即使 `ALLOW` 也只拿到 ×1.0，只是会播暴击动画。所以"必定暴击"必须走我们自己的 `forceCrit`，原版的 `ALLOW` 一律不用，我们只用 `DEFAULT→DENY` 把原版那一格关掉。
  - 与设计文档一致：附加结构（我们的 `damage` 独立一发）会重走管线 ⇒ 天然"按面板暴击"，正好符合 `06:6450`，不需要新原语。
  - 随机源要可测：暴击判定要能吃一个可注入的 `Random`，否则无头断言不稳定（原版 `level.random` 直接用会让门时绿时红）。

我打算按 C 落地，除非你们对第二节那四条另有说法。默认值（**没人回话就按这个做，回话就改**）：初始暴击率 **0%**、`暴击倍率 = 1.5 × (1 + crit_damage)`（1.5 沿用原版手感，`+20% 暴击伤害` ⇒ ×1.8）、暴击率不设上限、"必定暴击"= 这一次概率视为 1（不与概率二次判定叠加）、`critRequiresFullCharge` 那种"没蓄满不算暴击"的开关**先不做**（属蓄力线，等那条裁定）。

## 四、顺带挖出来的一处我们的语义错误：`direction_bonus`

对照他为什么把"方向增伤"挂在元素轴上，我去正本核了"方向卡"到底指什么，结果发现**我们两边的理解都不是正本，而我们错得更实**：

- **正本**：`00:132` 公式 `… ×（1+专属buff增伤）+ 方向增伤`、`00:156` "＋ 方向增伤 ｜ **方向卡带来的其他类型伤害** ｜ 中期"、`02:304` "**最外层加法区**，默认上限 120%，「超限」类可以突破"。而他的 60 张"方向卡"就是 **燎原 / 惊雷 / 寒霜**（火/雷/冰三系，`cards.json` 里 `layer=方向` 的 pool 分布 20/20/20）。⇒ **"方向"指的是流派方向（元素那一族），不是几何方向；而且它是最外层的加法项，不是乘区。**
- **他**：`elementMul = 1 + directionBonus + elementBonus + spec.extraDirectionBonus`，只在**元素轴**生效 ⇒ 对象搞对了（元素那一族），但仍做成乘区、且只挂元素轴。
- **我们**：`AttackPipeline.Step.DIRECTION` 是 `× (1 + 方向增伤)`，并且**按"这一发是否落在目标背后 120°"决定吃不吃**（`CardCombat.attackInputFor` 的 `directionApplies`），示例卡「双牙」+30% 与 GameTest `directionBonusNeedsTheActualContact`（正面 10 点、背后 13 点）都是照这个语义钉的。⇒ **我们把"背刺"实现成了"方向增伤"**：正本里几何那一族叫**背刺**（`02:642`：背后 120° 攻击**额外一次 30% 独立伤害**，必满足未察觉），而"方向增伤"是元素流派的最外层加法。唯一对上的只有"默认封顶 120% + 超限才能突破"（`DIRECTION_BONUS_CAP`，这条我们是对的）。

**建议的改法**（要你们点头才动，因为它改的是已验收的语义与一张示例卡）：

1. `channel.direction_bonus` **归还给元素流派**：语义按 `02:304` 做成管线**最外层加法**（在 `FLAT_THIS_SOURCE` 之后、`DELIVER` 之前），默认封顶 120%、`uncapped` 才突破；**在元素线落地之前它仍是"无落点"通道**，我会照实标出来，不会假装能用。
2. 新增 `channel.backstab_bonus`（正名建议就叫这个，中文名"背刺增伤"），形状按 `02:642`：**背后 120° 命中时额外结算一次独立伤害**（系数即卡面百分比），而不是乘区。这样"双牙"那种卡面能原样表达，且与"未察觉/处决"共用同一套几何判定（我们已经有 `back_sector` / `angle` / `unseen` 与 `DamageContact.angleOffFront`）。
3. 示例卡 `twin_fang` 从 `direction_bonus` 改到 `backstab_bonus`，GameTest 跟着改判据（正面不额外结算、背后额外一发），并把 `Mechanics` 里 `direction_bonus` 的 `Combine`/说明同步更新。

这一改动会牵动：`Mechanics`（通道表）、`AttackPipeline`（新增一步 + 把方向增伤挪到最外层）、`CardCombat.attackInputFor`、`cinder_step`/`twin_fang` 两张示例卡、两条 GameTest、以及《机制词表》第三节那两段关于方向增伤的说明。工作量大概一批（含门），但**必须先有你们对"方向增伤=元素流派最外层加法"这句确认**——因为它同时否掉了我此前的实现和另一作者的理解。

# 对照：另一作者的 powerlevel（496 张生成表）× 我们的词表

日期 2026-09-29。对象是 `powerlevel-0.1.0.jar`（作者 EEEABmobs，mod id `powerlevel`，"星图加点 · Power Leveling（半成品）"，`license = All Rights Reserved`），由作者本人同意**反编译阅读**后做的对照分析。

**边界先说清**：本文件只记录"他怎么做的"与"我们的缺口有多大"，**没有搬他的任何代码或资源进本仓库**。他的工程是 ARR，要复用实现需要另一句明确授权；今天这份对账用到的只有他自己生成表里的**卡名、字段取值与统计数**，属于口径层面。

分析对象还有两点值得知道：他与另一个人的 `powercards`（卡池模块）分工并行，靠 `CardSource` 接口对接；他的表是从 `设计文档\细化` **机器生成**的（`meta.generated = 2026-09-26 12:44:32`，`total 496 = 券 5 + 方式 436 + 方向 60`，另记 `skipped: 待开发 18 / 归档 19`）。

## 一、他是怎么做的（一句话版）

卡的数据只到"**一条中文效果文本 + 一组中文数值项**"，效果**不在 JSON 里**——每张卡的行为是写在 Java 里的：`forge/pools/` 与 `forge/direction/` 共 12,560 行（占非客户端代码的 51%），里面按卡名分支，全仓 `PlayerCards.has(player, "卡名")` 有 **211 处、涉及 150 个不同卡名**。他比我们多的是**运行时广度**（战斗事件总线、带时长的状态集、资源衰减、局账本、星图与推荐器、元素与抗性、暴击与穿透、召唤物、HUD 同步、11 种封包、命令、成就）；少的是**契约**（效果不可校验、引擎里写着内容字面量、装载无条数对账）。

## 二、方法（可信度分两档）

- **脚本初筛**：对 496 张的 `nums + effect` 跑关键词表，统计"这张卡需要哪种机制"。一张卡可以命中多项，所以各项之和 > 496。
- **人工抽样**：对每个大桶抽 3–8 张读原文，把正则虚高的部分扣掉。**下表"抽样修正"列就是人工核的结论**，没核过的桶一律标"未核"。

## 四、他的 stat 词表 → 我们的 16 通道

他 496 张里 495 张带 `stats`，共 30 种中文数值名。按能不能并进我们现有通道分三类：

- **同义词，直接并入**（不改引擎，只补一张中文说法对照表）：`护甲`→`armor`、`最大生命值`/`基础生命值`→`max_health`、`攻击速度`→`attack_speed`、`全伤增幅`/`全伤加成`→`all_damage`、`基础近战攻击力`→`base_damage`、`物理攻击增幅`/`物理伤害`→`physical_damage`、`方向增伤`→`direction_bonus`、`近战增伤`→`melee_damage`、`反伤倍率`→`reflect`（我们有动作无通道）、`移速增幅`/`移速`→`move_speed`（注意他按 `unit=="%"` 分流点值与比值，与我们"点值/比值不混"同型）。
- **当时没有落点、现在已落**：`暴击率` 56 张与 `暴击伤害` 44 张（2026-09-30，`CritRules`）、`护甲值` 54 张（落属性，更早）、`吸血` 6 张（2026-10-03，`Lifesteal`）。**仍然没有落点**：`抗性`（要等元素与伤害分类那一族）、`基础攻击力` 8 张（`base_damage` 的口径未定：是替掉面板还是再加一格）。
- **我们完全没有的**：`冰伤` 18 / `火伤` 16 / `雷伤` 14（**元素伤害一族**，配套还要一张抗性表）、`智慧` 13 / `幸运` 11（宏属性，抽卡与掉落要用的话是另一条线）、`血池上限` 12（可用 `stack.<id>.cap` 表达，但要先把"血池"命名成一个体系）、`全属性` 1（乘所有属性）。

高频词的量级摆在这里：`近战增伤` 104、`暴击率` 56、`护甲值` 54、`移速增幅` 47、`暴击伤害` 44、`生命上限` 30、`攻速` 21。**"暴击到底怎么算"这句裁定压着 118 张卡**（其中 **100 张卡的 `stats` 里就带着暴击率/暴击伤害数值**，去重后仍是全表第二大族），它现在是我们单条最大的阻塞项。

## 五、不打算跟的三条（写下来免得下次再议）

1. **按卡名分支的行为实现**（150 个卡名硬编码在 Java 里）——与我们"定制效果不定制卡"直接冲突，且他 `core/` 里写着 `"数值池".equals(pool)` 这类内容字面量，我们的 G2 门连注释都拦。
2. **一个字段收 18 个别名的宽容解析**——写错的键会静默变成"这项没写"，是我们记忆里 DFU 三层静默的同型问题。
3. **装载无条数对账**（解析失败 `catch → warn → 跳过单张`）——表现是"模组正常启动、内容少了几张"。我们那条 `contentReloadLoadsEveryFile`（加载数 == 磁盘数）成本极低，不要向他靠。

## 六、这份对账改变了什么

- 我们三份覆盖表此前只逐张核过 **45 张**，"其余约 365 张未逐张核对"。这次至少把**量级**拿到了：暴击 118、打断 34、精英归类 29、蓄力 26、放置与链 26、多段 25、召唤 21、领域 18、按目标作用域 16、元素 48 张带元素数值。下一批的顺序应当按这张表排，而不是按我们手上那 45 张的分布拍。
- 三条"要不要做"的判断题有了数据：**元素与抗性**是一整族（48 张带元素数值）而不是一张卡的特例；**召唤/假身**需要实体与归属账（21 张）；**主动技能栏**是独立子系统（真需求约 20 张，不是 44）。
- 他那份乘区实现（`Damage.compute` 的 8 个乘区 + 平加不进乘区 + 方向增伤默认上限 120% 可被"超限类增益"解除）与我们 `AttackPipeline` 的形状**互相印证**；他先落地而我们留空的正是暴击、穿透、上限解除这三条——也就是等裁定的那三条。
